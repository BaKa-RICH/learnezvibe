## 设计要点

1. **声明面**:`Contract.delivery_mode: str | None = None`,合法值 `pr | content`;缺省/None = pr(旧 manifest 零改动,向后兼容)。非法值走 lint 报错(fail-closed,对齐 omac 风格:保留非法输入报可修复错误)。
2. **策略模块**(单一事实来源):新建 `src/omac/core/delivery.py`
   - `DeliveryMode` 枚举(PR/CONTENT)
   - `resolve_delivery_mode(contract) -> DeliveryMode`(含非法值透传给 lint)
   - 差异点查询函数:如 `requires_pr_base(mode)` / `requires_pr_url_evidence(mode)` / `requires_merge_closure(mode)`--lint/evidence/loop/mock 只调这些函数,**不出现散点 if**
3. **差异点路由**(逐锚点,顺序即实施顺序):
   - lint.py:pr_base 检查加策略判断(仅 pr 模式必填)
   - evidence.py:`_has_pr_url` 检查仅 pr 模式;content 模式无替代硬门(B2 最小化,产物校验留给既有 verification 通道)
   - loop.py:merge 收口入口加策略判断,content 节点跳过 merge 确认直达 done
   - mock.py:auto-complete 的 develop 分支按模式分叉:pr -> 假 pr_url(现状);content -> 产物型 artifacts + verification
4. **TDD 红测试先行**(总纲给的测试思路):
   - 红 1:content 节点 manifest(零 PR 字段)过 lint
   - 红 2:content 节点 evidence 校验无 pr_url 仍过门(验证命令验收生效)
   - 红 3:content 节点完成无 merge 收口
   - 回归护栏:现有全部测试绿(PR 形态不变量)
