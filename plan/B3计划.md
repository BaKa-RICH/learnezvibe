## Overview

在同一冻结输入、同一角色 agent 配置、同一 `collect -> write -> review` 业务拓扑和同一验收目标下，对比 Multica Native squad 编排与 OMAC 编排。每组取得 2 个有效正式样本，共 4 个有效样本；`WEEK-9` 只作预演模板，不计入样本。| Workflow: full-pipeline | Gate: standard

Escalation: Task -> Wave -> Stage -> Project -> Human

### 目标与边界

- Native 组：每次新建一个根 issue 并指派给“周报” squad。根 issue 明示三个阶段及其顺序；leader 自主拆解、选择成员、派发和推进。不得规定附件、评论、仓库或其他交接媒介，实际交接方式属于观测结果。
- OMAC 组：每次新建一个根 issue，任务正文与 Native 使用同一个冻结模板；manifest 固定同一三节点 DAG，并把 collect、write、review 分别映射到对应的三个相同角色 agent。
- Native 与 OMAC 都必须真实完成 `collect -> write -> review`，不得把节点间产物传递从题面删除，也不得用人工搬运替代被测系统的传递。
- B3 只从 B4 抽取一段硬前置：真实 `content submit`、deliverable 持久化和下游读取。B4 的 reviewer reject、rework、再次评审和最终收口另行执行，其 run、token、耗时和步骤均不得混入 B3。
- B3 不声称统计显著性。N=2 用于得到可复核的基线样本；报告逐样本原始值、组内均值和范围，不以小样本推导普遍结论。

### 公平性合同

1. 四次正式执行共用一个已冻结的 Git revision 和输入清单；每个 workdir 在启动时验证实际 HEAD 与冻结值完全相等，输入文件另存 SHA-256 清单。
2. 四个根 issue 使用同一份任务正文、交付物名称和验收标准。只允许加入该编排方式必需的控制信息，这些差异必须逐项记录。
3. 三个业务角色使用同一批 agent 及相同的逐角色模型、thinking level、runtime 和工具配置；正式执行前保存脱敏配置快照。
4. Native leader 的拆解和交接保持自主。leader 自身产生的调用属于 Native 系统开销，计入该样本，不从 token 或耗时中剔除。
5. OMAC 基线不得让 final review 同时经历“review worker + OMAC reviewer”两次模型调用。基线 manifest 采用 `weekly-review` 作为 review 节点唯一 worker，不配置额外 reviewer；B4 才启用 reviewer 收敛机制。开跑闸门以实际 run 拓扑证明每个业务节点只有一个对应角色主调用。
6. 四个样本配对并发执行：`Native-01`+`OMAC-01` 同窗、`Native-02`+`OMAC-02` 同窗（同一环境窗口配对比较）；禁止同一 arm 两样本并发或四样本全并发（2026-08-20 修订，见 protocol.md）。

### 样本与结果判定

| 项目 | 定义 |
|---|---|
| 正式样本 | 通过全部前置闸门后创建的全新根 issue；预先登记为 `native-01`、`omac-01`、`native-02`、`omac-02` 之一 |
| 成功 | 三个业务节点按顺序完成；最终周报通过共同验收；平台状态、产物、run、message、usage 和时间证据均可关联到该根 issue |
| 失败 | 样本已正式开始，但因编排、agent、OMAC 或平台行为未达到成功条件；失败仍计入分母并保留已消耗 token、耗时及事件 |
| 排除 | 正式业务执行前遭遇外部取消、错误 revision、配置漂移或关键遥测缺失，导致样本不可比较；记录原因且不并入成功率/失败率，并用全新 issue 补足该组有效样本 |
| 成功率 | `成功数 / (成功数 + 失败数)`，按组和总体分别报告 |
| 失败率 | `失败数 / (成功数 + 失败数)`，按组和总体分别报告 |
| 排除率 | `排除数 / 全部正式尝试数`，单列；排除不得伪装为失败，也不得静默删除 |

## Execution Model

| Plan Element | Layer | Role |
|---|---|---|
| Stage dispatch | L0 Project | Selects workflow, sequences stages |
| Stage execution | L1 Stage | Decomposes into waves, runs gate |
| Wave dispatch | L2 Wave | Dispatches parallel tasks, checks conflicts |
| Task execution | L3 Task | **Only layer that does work** |

所有层间交接使用 TaskDispatch / StatusReport 结构化消息；L0-L2 只调度、验闸和升级，只有 L3 执行文件、Shell 或平台动作。任何阶段只有在前一阶段 gate PASS 后才能开始。

### 指标字典

| 指标 | 原始字段与计算方式 |
|---|---|
| 四类 token | 对每个样本 lineage 中所有去重 issue/task usage 行分别保存 `total_input_tokens`、`total_output_tokens`、`total_cache_read_tokens`、`total_cache_write_tokens`。平台 issue summary 只汇总该 issue，因此样本级值必须覆盖根 issue 与全部子 issue，并按唯一 issue/task id 防重复。 |
| Headline total | `total_tokens = total_input_tokens + total_output_tokens + total_cache_read_tokens + total_cache_write_tokens`。该公式与 Multica 后端 `GetIssueUsageSummary` 的字段以及前端 total 口径一致。 |
| Uncosted | 同时保存 `uncosted_input_tokens`、`uncosted_output_tokens`、`uncosted_cache_read_tokens`、`uncosted_cache_write_tokens`。它们是四类 total 中 `cost_usd_ticks IS NULL` 的子集，只用于透明披露，**不得再次加进 `total_tokens`**。 |
| 端到端耗时 | `wall_clock = max(所有验收所需终态 run.completed_at) - 正式根 issue 首个计量 run.started_at`。包含排队、leader/编排、节点等待和交接时间；时间统一保存 UTC 原值并可另显示上海时区。缺任一端点则该样本遥测不完整。 |
| Run active duration | 每个实际 run 单报 `completed_at - started_at`，并按角色、leader/控制 run、额外 run 分类；同时报告总和，但不得用总和替代端到端耗时。 |
| 步骤数 | 主指标为样本 lineage 内平台 run-message 事件记录数：按唯一 message/event id 去重，保存 run id、时间、方向/类型和原始记录。另报固定业务节点数 `3` 与实际 run 数（唯一 run id 数）。不得把人工感知的“操作次数”混称为步骤。 |
| 产物传递 | 保存 collect 输出、write 输入、write 输出、review 输入的 SHA-256 与 source/ref 关系；哈希相等和 ref 可解析是传递成功证据，不能只凭最终文本存在。 |
| 结果质量 | 使用共同验收 rubric 记录 pass/fail 和理由；不得让某一组获得额外人工润色或追加提示。 |

### 执行限制

- 不输出完整 Git remote URL、token、cookie、Authorization header 或其他凭据；配置快照必须脱敏。
- 所有平台写操作只发生在用户批准后的计划执行阶段，并限制在明确创建的 smoke/正式 issue；不得修改既有 `WEEK-9` 事实。
- 正式样本开始后不得临时改 prompt、agent 参数、manifest、revision 或验收规则。确需变更则作废整个基线批次并升级用户决定。

- 代码改动遵守 TDD；错误必须说明缺什么、如何修复并给出可复制命令；退出码合同保持兼容。
- Web routing 只解析参数、调用 command、原样返回 JSON；不得读取 manifest、调用 engine 或转换实验数据。

## Invariants

- P1: L0-L2 dispatch only; only L3 Tasks execute work.
- P2: Token budgets - L0: ~3K, L1: ~5K, L2: ~4K, L3: ~8K.
- P3: Inter-layer messages use typed YAML (TaskDispatch/StatusReport).
- P4: Every loop has max_iterations; failures are classified as retry / escalate / abort. B3 的样本失败不是可无限重跑的 convergence loop。
- P5: Layers communicate through artifact files, not conversation history；后续阶段必须读取上游 artifact 路径和原始证据，不能依赖口头摘要。
- Repository invariant: pipeline/CLI 只消费 `WorkItemStore` 与 `AgentRuntime`；平台 CLI 仅封装在 engine adapter。
- Experiment invariant: 两组始终为相同 `collect -> write -> review`、相同冻结输入、相同角色 agent、相同验收；Native 交接媒介自主，OMAC 交接由受测 content deliverable 通道完成。
- Accounting invariant: `uncosted_*` 是 `total_*` 的子集；不重复加总。预演、取消、smoke、排除样本和 B4 返工数据均不进入四个有效样本的 headline 比较。
